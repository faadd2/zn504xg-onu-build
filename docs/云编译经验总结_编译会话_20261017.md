# 云编译经验总结（编译会话视角，build-1 ~ build-26）

> 用途：删库重建后新仓库编译工作的参考底稿。由编译会话（B）沉淀，2026-10-17。
> 配套文档：《OpenWrt单包CI编译避坑清单_20261015.md》（单包编译八层坑详解，本文不重复展开，只索引）。
> 适用对象：下一个接手编译的人（人或 AI 会话）。读完应能独立完成：dispatch、排障、门禁维护、Release 发布、新包接入。

## 一、顶层格局（先建立正确的心智模型）

1. **构建链路**：`faadd2/zn504xg-onu-build`（CI 仓库，workflow 在这里跑）→ checkout `huladabang/ponwrt@master`（实际钉在 c3b518b，2026-09-29 后无新提交，ponwrt 的 master 就是 c3b518b）→ 注入我们的 kernel-patches/dts-patches/files 叠加层/自定义包 → 双矩阵腿（onu-suite / stock）编译 → Release `build-N`。
2. **补丁三层都要算进基线**：ponwrt 对 vanilla 6.18.52 的改动分三层——`target/linux/generic/patches-6.18`（458 个：backport 175 + hack 71 + pending 212，实证零触碰 airoha 驱动文件）+ `target/linux/airoha/patches-6.18`（163 个，全碰 airoha）+ 内核版本钉（`target/linux/generic/kernel-6.18` 写 6.18.52）。**IWRT/naoki66 树钉 6.18.55，与 ponwrt 补丁不可跨用**（跨则 160-v7.2-RX-headroom 类补丁硬挂）。
3. **quilt 按文件名序应用补丁**——这一条是 build-25 一案的根源，见踩坑 #1。
4. **账号纪律**：faadd2 的库只用 faadd2 PAT 推，faadd22 只用 faadd22 的，跨账号同步一律走本地库。fine-grained PAT 的已知边界：推内容必须在授权清单内；`rerun-failed-jobs` API 对 fine-grained PAT 返 403——重跑失败任务=重新 dispatch 一次。

## 二、十条铁律（每次动手前默读）

1. **dispatch 前确认三树同步**（本地=faadd22=faadd2），先 `git fetch origin && git log --oneline origin/main -3` 防对方会话插提交。
2. **失败不要原样重跑**——先定根因再触发，否则会再烧 2.5 小时（build-25→26 的教训：定位 40 分钟，重跑 2.5 小时）。
3. **日志 > API 元数据**。runs API 的 `inputs:{}` 不可信（build-22 voice 参数误判案）；判读一律看 job 日志正文。
4. **静默失败显式化**：grep 不到就加 `ls`、`echo`、校验步骤硬失败；V=s 重跑看首因（easycwmp 连败链的总结训）。
5. **中文 commit message 用 `git commit -F 文件`**；中文 API 负载写 JSON 文件 `curl -d @file.json`（Git Bash 的 printf/sed 会 GBK 污染，血的教训）。
6. **网络重试成惯例**：api.github.com 间歇超时，curl 一律 6-8 次重试间隔 6-10s；匿名限额 60 次/IP/时，查公开信息用 `git ls-remote` 代替 REST。
7. **任何校验都要硬失败**（`|| exit 1`）：grep 到 0 设备/缺包/版本不符时让 job 红，不要打警告继续——defconfig 会静默丢弃不存在的符号（设备符号前缀写错案、Kconfig 交互提问卡死案）。
8. **Release 资产会过期**，重要成品要么归档（archive-run.yml）要么落本地；发布说明必须写"本版改进了什么"（对照上一 tag 的 commit 列表）。
9. **新包接入先对照自查表**（见《单包避坑清单》末节 9 项），编译会话不猜 Makefile 语义。
10. **不动设备**：504 的验证一律 A 会话做；B 的验收=日志判读 + Release 资产流式核对（`list_tarzst.py`，注意脚本内 PAT 需随轮换更新）。

## 三、踩坑档案（按主题，含案例定位）

### 补丁与基线（最贵的一课）

**#1 build-25：补丁序号=应用位置，上下文不能向后依赖** ★★★
- 现象：双腿在 kernel `.prepare` 阶段同挂，`201-06` eth.c 1/2、ppe.c 3/18 hunks FAILED。
- 根因：补丁上下文引用了 925/930 等**文件名排在它后面**的上游补丁引入的代码；quilt 在 201 位置（中途）应用它，那些代码还不存在。
- 修复：内容一字不动，改名 `940-`（排在 ponwrt 930 之后）。glob 拷入机制下零 workflow 改动。
- 规则：**依赖上游补丁的自定义补丁，序号必须大于被依赖者（940+ 是我们的插尾部段）；或不依赖任何上游补丁时才能用 201- 段。**

**#2 补丁验证基线必须= quilt 真实顺序下的目标位置状态**
- 「在 163 补丁全量态验证零 fuzz」≠「能在 201 位置应用」。
- 正确的本地复现法（build-25 实证 40 分钟闭环）：
  ```sh
  # 1. kernel.org 流式解包（只要 airoha 目录就 ~145MB 流量，全程本地几分钟）
  curl -sL https://cdn.kernel.org/pub/linux/kernel/v6.x/linux-6.18.52.tar.xz | \
    tar -xJ --strip-components=1 -C 目标目录 --wildcards "*/drivers/net/ethernet/airoha/*"
  # 2. ponwrt 补丁稀疏克隆（blob:none 省空间）
  git clone --depth 1 --filter=blob:none --sparse https://github.com/huladabang/ponwrt
  git sparse-checkout set target/linux/airoha/patches-6.18
  # 3. 按文件名序循环 patch -p1 -f，记录每个 fuzz/offset/FAILED
  # 4. 要验证「中途位置」就打反向补丁把排在后面的回退掉再正向重放
  ```
- 注意：此法只覆盖 airoha 163 补丁；generic 458 个补丁实证零触碰 airoha 文件，涉及其他子系统时必须并入（三层目录都在 `target/linux/{generic,airoha}/patches-6.18`）。
- 佐证参考值：应用完全部补丁后 airoha_eth.c=5092 行、airoha_ppe.c≈1953 行。若你重建的基线行数差很多（如 3336），说明补丁没净生效，**在那棵树上写的补丁对 CI 没有参考价值**（A 侧旧树案）。

### Kconfig / 配置注入

**#3 顶层 .config 的 CONFIG_* 不进内核树**（SND_* 交互提问卡死 syncconfig 案，v7b）——内核符号的正确通道是子目标 `config-6.18` 片段（`target/linux/airoha/config-6.18`）。

**#4 kconfig.pl 只接受二元表达式**——3 文件合并 Parse error；两趟合并或 `cp 种子配置 && cat 片段 && make defconfig`（naoki66 官方用法）。

**#5 设备选择符号的层级**（build-15~17 三连丢设备案，target-metadata.pl 实证）：
- `choice Target Profile` 内 `MULTI_PROFILE=y` 与 profile 层设备符号**互斥**——profile 层写设备=反模式；
- 正确姿势：只写 `MULTI_PROFILE=y` + per-device 层 `CONFIG_TARGET_airoha_an7581_DEVICE_znxt_zn504xg-d=y`（前缀是 `CONFIG_TARGET_<target>_DEVICE_<profile>`，写成 `CONFIG_TARGET_DEVICE_...` 是不存在符号，defconfig 静默丢弃后 choice 回退默认设备 gemtek）；
- 门禁=三层全部硬校验。

**#6 luci.mk 系包 Makefile 必须带 `# call BuildPackage - OpenWrt buildroot signature` 注释**——缺了被 scan.mk 文件清单过滤，defconfig 时符号根本不存在（v1~v4 自定义包从未进固件的根因）。

### workflow / CI 工程

**#7 codeload 归档根目录名要探测**：openwrt-24.10 的 tarball 根目录是 `openwrt-openwrt-24.10` 不是 `openwrt-24.10`，tar 硬编码路径 11 秒挂（`4dca96c` 修复：`tar -tzf` 先探根目录）。

**#8 workflow_dispatch 输入设计**：参数全部 `required: true`（曾发生默认值推断与实际不符的争议）；dispatch 返回 204=成功，无 body。

**#9 workflow 里的相对路径步骤要警惕 cwd**：`git -C ponwrt apply 相对路径` 会被解析到 ponwrt/ 内秒挂（69da58d 案）——注入步骤统一用 `${{ github.workspace }}` 绝对路径。

**#10 manifest 硬门禁**（b9f42af 落地，打包前拦）：EN8811H 驱动+固件两腿必检、必备包清单（luci-app-onu 全链、migrate、ppp=2.5.1 等）逐包 grep。比事后翻固件快得多。

**#11 Windows 权限位**：git 索引里的 755 才不会进固件丢执行位（644 进固件导致插件假死案）；workflow 注入步 chmod 双保险。

### 单包编译（easycwmp 九跑八败）

完整八层坑（tools/toolchain 竞态、libmicroxml BUILDROOT、MAKE_FLAGS 被覆盖、autoreconf 静默跳过、AM_INIT_AUTOMAKE 重复、-fno-common……）见 **《OpenWrt单包CI编译避坑清单_20261015.md》**（`devices/ZN504XG-D/reports/`），此处只留结论：**这类"静默跳过"型失败必须显式化 + V=s 重跑看首因**；单包 CI 用 `make package/x/compile` 而非 world；`MAKE_FLAGS` 赋值必须写在自己 include `package.mk` 之后。

### 发布与资产

**#12 tar.zst 资产核对用流式列表**（不下载全包）：`list_tarzst.py <Release资产URL>` 列内容核对 manifest；固件镜像单独流式提取（zn504 sysupgrade .itb 约 14MB）。

**#13 Release 格式**：用户要求 Windows 友好（zip/7z 诉求出现过）；资产命名含腿/设备/类型；sha256sums 随包。

## 四、操作速查（新库第一天）

```sh
# 触发双版本编译（build-27 起接编号）
curl -X POST -H "Authorization: Bearer $PAT" -H "Accept: application/vnd.github+json" \
  https://api.github.com/repos/faadd2/zn504xg-onu-build/actions/workflows/build.yml/dispatches \
  -d '{"ref":"main","inputs":{"ponwrt_ref":"master","onu_suite_ref":"main","voice_kernel_patches":"yes"}}'
# 204=已触发；查 run：/actions/runs?per_page=3；查 job 进度：/actions/runs/<id>/jobs

# 三方同步检查（本地=faadd22=faadd2）
git fetch <remote> main && git diff --stat HEAD FETCH_HEAD   # 无输出=同步

# 失败日志下载
curl -s -H "Authorization: Bearer $PAT" \
  https://api.github.com/repos/faadd2/zn504xg-onu-build/actions/jobs/<job_id>/logs > tmp.txt
```

**验收清单（每次 build 发布前过一遍）**：
1. 双腿结论 success；2. Release 资产齐全（images tar + packages + sha256sums，双腿分明）；3. `list_tarzst.py` 流式核对 manifest 硬门禁包全在；4. 固件 itb 大小合理（zn504 ~14MB，明显偏大=设备没裁剪成功）；5. 发布说明写「本版改进」（对照上一 tag diff）；6. SESSION-SYNC 记录 run id + 构建号 + 内容快照点。
